Überblick

Spring Boot 4.1.0 / Java 25, MariaDB via JPA, drei Frontends auf einer Codebase: Thymeleaf (/), Vaadin Flow (/app/*), Hilla/React (src/main/frontend) plus versionierte JSON-API (/api/{version}/...). 3 isolierte SecurityFilterChains. Der interessante Teil ist die Order→Fulfillment→Picking→Packing→Shipping-Kette; der Rest ist weitgehend CRUD.

Der Arbeitsstand ist deutlich Work-in-Progress: viel uncommitteter Code, viel auskommentierter Code. 64 Testklassen mit zusammen 594 Tests, alle grün (Stand 2026-10-05). ApplicationTests (Context-Load), CustomQueryExecutionTest (führt jede handgeschriebene @Query und jeden EntityGraph einmal aus) und ReservationDtoTest (braucht echte Hibernate-Proxies) starten den Spring-Kontext und brauchen eine erreichbare Datenbank, der Rest läuft mit Mockito/AssertJ bzw. Standalone-MockMvc in Sekunden.

3. Expiry-Sweep gibt ganze Orders frei, nicht nur das Abgelaufene

Reservation.expiresAt steht auf now().plusHours(1). AutomaticReservationService.tryToRelease() holt über FulfillmentService.findOrdersWithExpiredReservations() jede Order, die mindestens eine abgelaufene Reservierung hält, und ruft dafür releaseItems(order, "system") auf. releaseItems gibt aber alle aktiven Reservierungen der Order frei - es gibt keinen Weg mehr, nur einen Teil freizugeben.

Folge: Eine Order, deren Zeilen in getrennten Aufrufen reserviert wurden, verliert beim ersten Ablauf auch die frische Reservierung daneben, samt Bestand. Ist danach nichts mehr aktiv, fällt die Order auf APPROVED zurück, und tryToReserve() (nur IN_FULFILLMENT) holt sie nicht wieder ab.

Die @Scheduled-Annotationen in AutomaticReservationService sind während der Entwicklung bewusst auskommentiert - das ist kein Befund, relevant wird der Punkt beim Einschalten.

5. Rollenvergabe über /users ist ungeprüft

Ein- und Ausgabe sind DTOs: UserController nimmt UserRequestDto (dto.user) entgegen und antwortet mit UserDto (siehe "Erledigt"). id, userType, createdAt, lastLogin kommen nicht mehr an.

Der isActive-Punkt ist erledigt (siehe "Erledigt"): ein Update ohne das Feld laesst die Sperre stehen.

Offen: Welche Rollen der Aufrufer vergeben darf, prüft niemand. UserServiceImpl.update übernimmt die Rollen aus dem Request (existing.setRoles(user.getRoles())), create ebenso (prepareUserForCreate) - ein MANAGER kann sich selbst oder anderen ADMIN geben oder einen ADMIN anlegen; die erste Rolle entscheidet dabei auch den Benutzertyp (saveWithUserType). Lösung: nur ADMIN darf ADMIN (und ggf. MANAGER) vergeben, sonst 403.

- Ordernummer ist ein permutierter Zaehler (Stand 2026-10-05, war Befund 1): statt eine Zufallszahl
  zu ziehen und die Datenbank zu fragen, ob sie frei ist, wird ein dichter Zaehler bijektiv auf den
  Wertebereich abgebildet. Bijektiv heisst: zwei verschiedene Zaehler koennen nie dieselbe Nummer
  ergeben, es gibt also nichts zu pruefen und nichts zu wiederholen. Damit sind die Schleife, das
  TOCTOU-Race und die Endlosschleife bei Erschoepfung weg.
  Vier Teile: OrderNoSequenceMigration legt die Sequenz order_no_seq an (ddl-auto kann das nicht,
  sie haengt an keiner Entity), OrderRepository.nextOrderNoCounter zieht sie (native, NEXTVAL),
  OrderNumberScrambler permutiert, OrderServiceImpl.nextOrderNo setzt sie zusammen.
  Die Permutation ist ein vierrundiges Feistel-Netz - das ist eine Permutation, egal was die
  Rundenfunktion tut, weshalb die Garantie leicht zu halten ist; die Rundenfunktion entscheidet nur,
  wie zufaellig es aussieht. Bewusst kein id * Primzahl mod n: auch bijektiv, aber linear - alle
  benachbarten Nummern haetten denselben Abstand, aus zwei Ordernummern liesse sich der Rest
  ableiten. Der Test misst genau das (ueber 10.000 Paare keine zwei gleichen Differenzen).
  Die Blockbreite wird aus dem Wertebereich berechnet (halfBitsFor) und nicht hingeschrieben: cycle
  walking kostet BLOCK / COUNT Runden, bei einem Block, der nicht mehr zum Bereich passt, sind das
  ueber tausend statt 1,6.
  Belegt: der Test laeuft den GANZEN Bereich durch und haelt, dass es eine Bijektion darauf ist -
  eine Stichprobe koennte nur sagen "noch keine Kollision gefunden". Dazu CustomQueryExecutionTest
  fuer die Sequenz selbst (zwei Zuege, zaehlt hoch), weil kein Unit-Test sieht, ob die Sequenz
  ueberhaupt existiert.
  Der Bereich 90000..199999 traegt 110.000 Orders; die naechste wird mit klarer Meldung abgelehnt,
  statt eine Nummer doppelt zu vergeben oder sich aufzuhaengen. Er spannt zwei Stellenbreiten: eine
  Ordernummer ist fuenf- oder sechsstellig, und die ueber 99999 beginnen mit 1. Was fuer alle gilt,
  ist der Wert - nie unter 9000; eine einheitliche Breite oder eine fuehrende 9 gilt nicht.
  Der Bereich laesst sich nur aendern, SOLANGE keine Nummern im Umlauf sind: ein anderer Bereich ist
  eine andere Permutation, und ein Zaehler koennte dann auf eine Nummer fallen, die ein frueherer
  schon hatte. Dasselbe gilt fuer die vier Rundenkonstanten.

Offene Datenpflege (optional)

PFLICHT vor dem nächsten Reservieren - reservation.order_id ist NOT NULL, die Entity schreibt die
Spalte nicht mehr, jedes neue Reservierungs-Insert scheitert sonst:
      SHOW INDEX FROM reservation;              -- nachsehen, ob ein Index order_id enthält
      ALTER TABLE reservation DROP COLUMN order_id;

Alle bisher hier gelisteten Migrationen sind erledigt (siehe oben). Übrig ist Kosmetik:

- shipment_package.weight bestehender Pakete: 0 oder ein früher angegebener Wert, bis das Paket
  das nächste Mal geändert wird. Einmalig nachrechnen:
      UPDATE shipment_package sp
      SET weight = COALESCE((SELECT SUM(pi.quantity * COALESCE(p.weight, 0))
                             FROM package_item pi
                             JOIN order_items oi ON oi.id = pi.order_item_id
                             JOIN products p ON p.id = oi.product_id
                             WHERE pi.shipment_package_id = sp.id), 0);

- 4 package_item-Zeilen ohne run_no. Jede als eigener Lauf:
      UPDATE package_item SET run_no = UUID() WHERE run_no IS NULL;
- 1 shipment_package ohne package_number. Nummer nachtragen, z. B. im Format von
  generatePackageNumber (PKG-yyyyMMdd-XXXXXXXX):
      SELECT id, created_at FROM shipment_package WHERE package_number IS NULL;
